JVM执行引擎

约 3919 字大约 13 分钟

前端编译与后端编译

Java的编译流程如下图所示，它通常需要将java语言转换成字节码文件，然后由JVM的执行引擎进行加载与解释执行。

Java的整个编译流程分为两个部分：

  • 前端编译：将高级语言（如Java源码）编译为中间表示（如Java字节码），发生在编译器。
  • 后端编译：将字节码或运行时中间代码转换为高度优化的本地机器码，主要指JVM的即时编译，发生在运行时。

前端编译

前端编译是指将Java源代码编译成Java字节码文件的过程，主要由javac编译器完成。前端编译发生在编译期间，它的主要任务是：

  • 词法分析、语法分析、语义分析；
  • 构建抽象语法树（AST）
  • 类型检查、注解处理
  • 生成与JVM规范兼容的字节码指令

它的特点是不涉及程序运行时的性能优化，目标是生成正确、可移植、符合JVM规范的字节码，是Java实现“一次编写，到处运行”的基础。

后端编译

后端编译是指将Java字节码在运行时转换为高度优化的本地机器码的过程，主要是由JVM的即时编译器（JIT）完成。JVM的即时编译器有两种实现，分别是客户端编译器（C1编译器）和服务端编译器（C2编译器）。后端编译的主要任务是：

  • 热点代码检测（比如方法被多次调用或循环执行很多次）
  • 将热点字节码编译为优化的本地机器码
  • 多层次优化：方法内联、逃逸分析、循环展开、常量折叠、死代码消除等
  • 生成平台相关的机器指令，直接运行在CPU上，速度极快

解释执行与编译执行

解释执行

在JVM启动时，不直接将字节码编译为机器码，而是通过内置的字节码解释器（Bytecode Interpreter），逐条读取.class文件中的字节码指令，并将其解释为对应本地机器操作，然后执行。

解释执行的特点就是实现简单，启动速度快，但是执行速度慢，它适用于短生命周期程序、启动要求极高的场景。

编译执行

为了解决解释执行慢的问题，JVM引入了即时编译器（JIT，Just-In-Time Compiler），在程序运行时，将那些频繁执行的热点代码编译为本地机器码，之后直接执行机器码，大幅度提升性能。

编译执行的特点是启动慢，执行快，优化能力强，它适合长期运行、有热点代码的业务系统、后端服务等。

JVM的执行模式（混合执行模式）

JVM既不是纯粹的解释执行，也不是纯粹的编译执行，而是两者结合：

  1. 程序启动时，先使用解释器快速执行字节码，立即相应，无需等待编译；
  2. 运行过程中：JVM会监控代码的执行情况，识别出热点代码；
  3. 热点代码触发JIT编译：JIT编译器将这些代码编译为高度优化的本地机器码，后续直接执行机器码，大幅提升性能；
  4. 分层编译：结合解释器、C1编译器和C2编译，实现启动快 + 运行后更快的平衡；

JVM编译执行的常用参数

参数作用说明
-Xint强制使用解释执行所有字节码只被解释执行，不开启 JIT，用于调试或对比性能
-Xcomp强制优先使用 JIT 编译尽量把所有代码先编译再执行，但可能导致启动变慢，实际很少用
-XX:+TieredCompilation启用分层编译（默认开启）结合解释器、C1、C2，平衡启动速度与峰值性能
-XX:+PrintCompilation打印 JIT 编译日志查看哪些方法被 JIT 编译了，用于性能调优分析

热点代码探测技术

热点代码是指被频繁调用的方法或频繁执行的循环体。HotSpot采用基于计数器的热点探测，它为每个方法维护两类计数器：方法调用计数器和回边计数器。

  • 方法调用计数器

    统计方法被调用的次数，与回边计数合并判断，超过阈值触发编译。

    默认阈值：Client模式约1500次，Server模式约10000次；可以用-XX:CompileThreshold=N来进行调整；

  • 回边计数器

    统计循环回边（向后跳转）的次数，用于识别循环体热点并触发OSR编译。

    直接阈值可通过-XX:BackEdgeThreshold设置，实践中常通过-XX:OnStackReplacePercentage间接调整回边阈值与编译时机。

当累计热度达到阈值，JVM会向编译器提交编译请求，编译完成后，方法入口被改写为指向本地机器码，后续直接执行优化后的代码。对于循环热点，使用栈上替换（On-Stack Replacement，OSR）在运行中解释执行的栈帧替换为编译后的版本，避免等待循环自然结束再切换。

探测流程与触发路径

  1. 解释执行开始，方法首次调用时检查是否已经有编译版本；若无，调用计数器加1；
  2. 判断：调用计数器 + 回边计数器 是否超过了阈值（或满足分层编译的动态策略）
    • 超过则向编译器提交异步编译请求，当前仍解释执行；
    • 编译完成后，方法入口被改写为编译后的本地代码，下次调用直接命中机器码；
  3. 循环体热点通过回边计数器累计，达到阈值后触发OSR编译，在执行过程中把栈上解释帧替换为编译帧，循环继续以优化代码运行；

长尾方法的解决策略

长尾方法是指在程序运行过程中，被调用频率很低、或者只被调用少数几次的方法。这类方法往往在整个程序的调用图中处于尾部，即调用次数少、对整体性能影响较小，但在统计上却大量存在。

在JVM的上下文中，长尾方法就是指：

  • 调用频率极低（比如只被调用1次，几次，或者整个运行周期内只被调用很少的次数）
  • 对程序整体性能贡献很小
  • 数量很多（比如：工具方法、回调、初始化方法、低频业务逻辑等）

JVM（特别是HotSpot虚拟机）中的JIT编译器，并不会把所有的方法都编译成机器码，而是只编译那些被分为是热点的方法，也就是被频繁调用、执行时间长、对性能影响大的方法。

长尾方法的调用次数很少，永远达不到热点阈值，因此它不会被JIT编译，始终以解释执行的方式运行，效率较低。如果这类方法数量很多，它们的计数器累加行为和检查开销可能会带来一定的性能负担或干扰。

JVM对于这个问题的优化策略就是：计数器衰减（Counter Decay）

定期对方法调用计数器和回边计数器进行衰减（通常是减半），以防止这些低频方法永远堆积计数、占用资源或干扰热点判断。

即时编译器（JIT）

JVM即时编译器（JIT）是在程序运行时，将字节码（bytecode）动态地编译为原生机器码（native machine code）的技术。JIT的主要作用就是提升程序的执行效率，它通过识别和优化“热点代码”来提高速度。这种结束结合了启动快和长期运行性能好的优点，最终使得Java程序长期运行时能够获得接近原生代码的性能。

核心工作流程

JIT的核心工作流程可以概括为：识别热点代码 -> 编译优化 -> 缓存执行三个核心的步骤。

  1. 识别热点代码：IT不会编译所有的代码，而是只针对频繁执行的代码（方法调用计数器+回边计数器）进行编译。

  2. 编译与优化：当代码被标记为热点后，JIT编译器会将其字节码转化为机器码，且这个过程会伴随一系列的深度优化（JIT提升性能的核心）；

  3. 缓存与执行：编译后的机器码会被缓存到代码缓存中，后续再次执行该热点代码时，JVM会直接从缓存中读取机器码执行，无需重新解释或编译。

    代码缓存的大小可以通过参数进行调整：

    • -XX:InitialCodeCacheSize：初始大小，默认值为2496KB；
    • -XX:ReervedCodeCacheSize：最大大小，默认值约为256M；

    若代码缓存满，JIT会停止编译，后续代码只能解释执行，可能导致性能下降。

HotSpot中的JIT编译器

HotSpot提供了两种JIT编译器，它们会根据运行模式自动选择：

特性Client Compiler（C1）Server Compiler（C2）
目标场景桌面应用、启动快优先服务器应用、长期运行性能优先
编译速度快（简单优化，编译开销小）慢（深度优化，编译开销大）
性能输出中等高（充分利用硬件特性）
适用场景短运行时间、交互型应用长运行时间、高并发服务（如 Java 后端）

默认的选择机制：

  • 32位VM：根据系统内存自动选择（内存小则Client）；
  • 64为VM：仅支持Server模式（64位应用多为服务器场景，追求高性能）；

此时JDK7引入了Tiered Compilation（分层编译），融合了C1和C2的优势：

  • 热点代码先由C1快速编译（保证启动速度）
  • 运行一段时间后，若代码仍然为热点，再由C2进行深度优化（保证长期性能）

分层编译默认开启，可以通过-XX:-TieredCompilation关闭，是目前服务器端Java应用的最优选择。

JIT的中的编译优化策略

JIT的核心在于其动态优化能力，JIT编译器会根据程序运行状态进行一系列优化，以提升执行效率。

方法内联（Method Inline）

方法内联是JIT最常用的优化技术之一，其基本思想是将小型、频繁调用的方法字节码直接嵌入到调用者的字节码中，避免实际的函数调用开销。

方法内联的优点在于：

  • 减少方法调用的开销：每次调用方法都会有压栈、出栈、传递参数的开销。内联后，这些开销可以被消除；
  • 提升优化的机会：内联后，更多代码暴露在一起，JIT可以进一步要优化，如常量传播和循环展开；

方法内联的局限性：

  • 代码膨胀：内联太多的方法可能会导致生成的机器码变得非常大，可能对CPU缓存不太友好；

方法内联的参数控制

参数作用说明
-XX:+Inline启动方法内联默认开启
-XX:+UnlockDiagnosticVMOptions
-XX:+Printlnlining		打印内联决策详情，用于定位内联成百与瓶颈与 -XX:PrintCompilation 联用以观察编译与内联过程
-XX:MaxInlineSize = N非热点方法能被内联的最大字节码代销
-XX:FreqInlineSize = N热点方法能被内联的最大字节码大小
-XX:InlineSmallCode = N目标方法编译后生成的机器码若超过该与之，则不进行内联避免生成过大的机器码
-XX:MaxTrivialSize = N被视为琐碎方法的与之这类方法更易被内联
-XX:MaxInlineLevel = N内联的最大嵌套调用深度
-XX:MaxRecursiveInlineLevel = N递归内联深度上限

死代码消除（Dead Code Elimination）

死代码消除是指移除程序中永远不会执行的代码，这类代码可能有雨编译时分支判断，或者是在方法调用中传入固定值导致一些条件永远不会被满足。

死代码消除的优点：

  • 提高执行效率：去除不必要的代码能减少指令执行的数量；
  • 减少代码体积：去除无用分支和逻辑可以缩减机器码的体积；

常量传播（Constant Propagation）

常量传播指的是将已知的常量值直接传播到程序中的其他地方。例如，如果一个变量的值在某个范围内是固定的，JIT 可以将其替换为常量。

常量传播是指，在编译器能够确定某个变量在程序运行时必定是一个固定的常量值，那么编译器就会直接把这个变量替换为它实际的常量值，从而避免运行时再去读取该变量，提升执行效率。

优点：

  • 减少计算开销：如果某个变量的值是常量，可以省去其余的计算步骤。
  • 增加优化机会：常量传播后，JIT 可以进一步应用其他优化策略，如分支消除。

逃逸分析

逃逸分析是JIT即时编译器在热点路径上对对象引用“可达范围”的静态/动态分析，用于判断对象是否会逃逸出当前方法或线程。

若分析结果为不逃逸，即可为后续的优化提供依据，如：同步锁消除、标量替换以及栈上分配。自JDK7后默认开启逃逸分析，该分析本身不是直接优化，而是为其优化“开绿灯”。

逃逸判定规则与典型场景

  • 方法逃逸：对象被当做返回值、存入实例字段/静态字段，或传入位置代码等，导致外部方法可以访问该对象；
  • 线程逃逸：对象被发布到其它线程可见为止（如赋给可其它线程访问的字段、放入共享容器、作为线程任务参数等）。
  • 不逃逸：对象仅在创建它的方法内被使用，且不会被发布到方法外或线程外；

判断要点在于：是否写入堆中字段、是否跨线程可见、是否传入位置代码，HotSpot在无法证明安全时采取保守策略，视为逃逸。

基于逃逸分析的优化与示例

同步对象锁消除

void foo() {
    Object o = new Object();
    synchronized (o) { System.out.println(o); } // 可能被优化为无锁
}

标量替换

class Point { int x, y; }

double work() {
    Point p = new Point();
    p.x = 1; p.y = 2;
    return p.x + p.y; // 可能被优化为: int x=1, y=2; return x+y;
}

不再从堆内存中为对象分配内存空间，字段访问改为局部变量访问，常配合寄存器分配进一步加速；

栈上分配

概念上可将不逃逸的对象分配在栈上，随栈帧退出自动回收；但HotSpot并未实现真正的栈上分配，实际以标量替换达成等价效果（对象整体分配被消除）。

JVM 参数与实践建议

  • -XX:+DoEscapeAnalysis：开启逃逸分析（默认开启；关闭用 -XX:-DoEscapeAnalysis）。
  • -XX:+EliminateLocks：开启同步消除（锁消除，默认开启）。
  • -XX:+EliminateAllocations：开启标量替换（默认开启）。
  • 诊断类（多为 debug 版 JDK 可用）：-XX:+PrintEscapeAnalysis、-XX:+PrintEliminateAllocations。
