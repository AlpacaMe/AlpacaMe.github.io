Spring MVC详解

Spring的基本使用

其实现在很多的应用都是基于Spring Boot构建的，很少再会用到Spring MVC的基础构建方式。但是为了帮助理解Spring MVC的工作流程，对于Spring MVC的使用方式还是有必要讲述一下的。

Spring MVC的启动流程

在web.xml文件中我们配置了一个Servlet，它的类型是org.springframework.web.servlet.DispatcherServlet类型，因此在项目启动的时候就会执行DispatcherServlet中的init()方法。

因为DispatcherServlet是HttpServletBean的子类，所以它的init()方法实际执行的是HttpServletBean#init()方法。在HttpServletBean#init()方法中主要是创建一些全局使用的Bean，最后执行会调用initServletBean()方法。

initServletBean()方法采取的模板方法设计模式，它由HttpServletBean的子类FrameworkServlet实现，所以最终调用的FrameworkServlet#initServeltBean()方法：

	// 去除了部分的日志打印相关的代码（避免干扰，只看核心的逻辑）
	protected final void initServletBean() throws ServletException {
		long startTime = System.currentTimeMillis();

		try {
            // 这一步很明显是去创建一个BeanFactory（具体的创建不在这里分析，可以参照Spring IOC原理来理解）
			this.webApplicationContext = initWebApplicationContext();
            // 初始化默认的Servlet用于用户请求的响应
			initFrameworkServlet();
		}
		catch (ServletException | RuntimeException ex) {
			logger.error("Context initialization failed", ex);
			throw ex;
		}
	}

初始化WebApplicationContext

创建WebApplicationContext

Spring MVC启动的第一个关键步骤就是创建一个WebApplicationContext（IOC容器），具体的执行逻辑在FrameworkServlet#initWebApplicationContext()方法中：

	protected WebApplicationContext initWebApplicationContext() {
        // 尝试从Servlet上下文中获取WebApplicatinContext
		WebApplicationContext rootContext =
				WebApplicationContextUtils.getWebApplicationContext(getServletContext());
		WebApplicationContext wac = null;
		// 如果已经获取到了WebApplicationContext
		if (this.webApplicationContext != null) {
            // 就将当前获取的WebApplicationContext上下文赋值给wac
			wac = this.webApplicationContext;
            // 如果wac的类型是ConfigurableWebApplicationContext，就让它与根容器建立父子关系
			if (wac instanceof ConfigurableWebApplicationContext) {
				ConfigurableWebApplicationContext cwac = (ConfigurableWebApplicationContext) wac;
				if (!cwac.isActive()) {
					if (cwac.getParent() == null) {
						cwac.setParent(rootContext);
					}
					configureAndRefreshWebApplicationContext(cwac);
				}
			}
		}
		if (wac == null) {
			wac = findWebApplicationContext();
		}
		if (wac == null) {
			wac = createWebApplicationContext(rootContext);
		}

		if (!this.refreshEventReceived) {
			synchronized (this.onRefreshMonitor) {
				onRefresh(wac);
			}
		}

		if (this.publishContext) {
			String attrName = getServletContextAttributeName();
			getServletContext().setAttribute(attrName, wac);
		}

		return wac;
	}

初始化DispatcherServlet

在Web应用的上下文容器创建完成后，就会执行刷新容器的上下文，这里会调用onRefresh()方法来刷新上下文。

onRefresh()方法采取的是模板方法的设计模式，它的具体实现在DispatcherServlet#onRefresh()方法中：

	protected void onRefresh(ApplicationContext context) {
		initStrategies(context);
	}

	// 执行Spring MVC中各大组件的初始化
	protected void initStrategies(ApplicationContext context) {
		initMultipartResolver(context);
		initLocaleResolver(context);
		initThemeResolver(context);
		initHandlerMappings(context);
		initHandlerAdapters(context);
		initHandlerExceptionResolvers(context);
		initRequestToViewNameTranslator(context);
		initViewResolvers(context);
		initFlashMapManager(context);
	}

这是Spring MVC中几大核心组件，它的作用分别是：

  • MultipartResolver：负责处理文件上传请求。当客户端提交包含文件数据的表单时，MultipartResolver会将HTTP请求包装成多部分请求，使得控制器方法能够通过@RequestParam注解方便地接受MultipartFile类型的文件参数。
  • LocalResolver：管理请求的国际化和本地化处理。它解决了当前请求地域的设置，使得应用能够根据用户的语言偏好显式相应的消息内容。常见的策略包括基于会话、Cookie、请求头或参数的本地化解析，支持内容的动态语言切换。
  • ThemeResolver：控制应用外观的主题系统。虽然现代Web应用较少使用，但它允许应用根据不同的主题（如颜色方案、布局样式）来渲染视图。主题解析器通常与主题资源解析器协作，为不同的用户提供视觉定制能力。
  • HandlerMappings：这是请求路由的核心组件。它负责将传入的HTTP请求映射到相应的处理器（通常是Controller中的方法）。映射的过程基于各种条件：URL模式、HTTP方法、请求参数、请求头等。Spring MVC提供了多种映射策略，如基于注解的@RequestMapping、基于XML的配置映射以及基于请求属性的灵活映射；
  • HandlerAdapters：充当DispatcherServlet和具体处理器之间的桥梁。由于处理器可能有不同的接口和实现方法（如基于注解控制、基于接口控制器、HttpRequestHandler等）。HandlerAdapter提供了统一的调用机制，常用的是RequestMappingHandlerAdapter，它专门处理基于注解的控制器方法。
  • RequestToViewNameTranslator：当控制方法没有明确指定视图名称时，这个组件会自动从请求信息中推导出视图名称。
  • ViewResolver：负责将逻辑视图名称解析为具体的视图的实现。它将控制器返回的字符串视图名转换为实际的视图对象。支持链式解析，可以按照优先级顺序尝试多个解析器，直到找到合适的为止。
  • FlashMap：管理重定向场景下的临时属性传递。在重定向操作中，某些属性需要跨请求保持，但又不应该长期存储在会话中。FlashMapping通过在会话中短暂存储这些“闪存”属性来解决这个问题，确保重定向后的目标请求能够获取到所需的临时数据。

其实对于现代化的Web应用而言，大多会采取前后端分离的模式来进行开发，前后端之间会采取JSON格式的数据传递。所以一般而言，后端不再需要进行时视图的渲染了，更多的是数据的提供。因此在Spring MVC中HandlerMappings和HandlerAdapters是极为重要的，它也是Spring MVC中的核心模块。

初始化HandlerMappings

对于HandlerMappings的初始化直接从DispatcherServlet#initHandlerMappings()方法开始：

	private void initHandlerMappings(ApplicationContext context) {
		this.handlerMappings = null;
		// 是否有扫描所有HandlerMapping类型的Bean
		if (this.detectAllHandlerMappings) {
            // 采取定扫描的策略，从IOC容器中获取到所有类型为HandlerMapping的Bean
			Map<String, HandlerMapping> matchingBeans =
					BeanFactoryUtils.beansOfTypeIncludingAncestors(context, HandlerMapping.class, true, false);
            // 如果HandlerMappng类型的Bean不为空
			if (!matchingBeans.isEmpty()) {
                // 根据他们的优先级进行排序
				this.handlerMappings = new ArrayList<>(matchingBeans.values());
				AnnotationAwareOrderComparator.sort(this.handlerMappings);
			}
		}
		else {
            // 不采取自动检测的策略，只获取beanName为handlerMapping的Bean
			try {
				HandlerMapping hm = context.getBean(HANDLER_MAPPING_BEAN_NAME, HandlerMapping.class);
				this.handlerMappings = Collections.singletonList(hm);
			}
			catch (NoSuchBeanDefinitionException ex) {
			}
		}

		// 根据不同的策略从IOC容器中找到对应的HandlerMapping的Bean
		if (this.handlerMappings == null) {
            // 如果找到的HandlerMappings为空，则按照默认的策略再找一次（自动扫描）
			this.handlerMappings = getDefaultStrategies(context, HandlerMapping.class);
		}
		// 这里是判断这个HandlerMapping对于路由解析的策略（兼容新旧版本两种）
		for (HandlerMapping mapping : this.handlerMappings) {
			if (mapping.usesPathPatterns()) {
				this.parseRequestPath = true;
				break;
			}
		}
	}

关键点：

  • detectAllHandlerMappings属性的含义：detectAllHandlerMappings = true表示自动检测所有可用的HandlerMapping类型的Bean，而不是仅仅寻找名为“handlerMapping”的特定Bean；

  • HandlerMapping.usesPathPatterns()方法返回boolean值：

    • 返回true：该HandlerMapping使用现代的PathPattern API（如Spring 5.3+的RequestMappingHandlerMapping默认配置）
    • 返回false：该HandlerMapping使用传统的AntPathMatcher

基于上面的初始化方法是非常好理解的，实际上就是将所有的HandlerMapping类型的Bean从IOC的容器中拿出来，然后放入DispatcherServlet的handlerMappings属性中。

所以重点是我们需要搞清楚HandlerMapping的作用，以及IOC容器中会存在哪些类型为HandlerMapping的Bean，这是重要的核心内容。

1️⃣先要搞清楚IOC容器会存在哪些HandlerMapping类型的Bean

所以我们先要搞清楚源码中存在多少种HandlerMapping的子类，观察HandlerMapping的实现类图，可以看到

一般而言存储在IOC容器中都会是非常具体的实现，所以我们只需要研究下叶子节点的类就好了。在上面的类图中，RouterFunctionMappiing、BeanNameUrlHandlerMapping、RequestMappingHandlerMapping、SimpleUrlHandlerMapping、PathPatternMatchableHandlerMapping。它们的作用分别是：

  • RequestMappingHandlerMethod：最常用的映射器，处理所有使用@RequestMapping系列注解的控制器方法；

    @RestController
@RequestMapping("/api/users")
public class UserController {
    
    @GetMapping("/{id}")
    public User getUser(@PathVariable Long id) { }
    
    @PostMapping
    public User createUser(@RequestBody User user) { }
}

  • BeanNameUrlHandlerMapping：基于Spring bean名称的URL映射，bean名称必须以斜杠开头才能被识别为URL映射；

    @Component("/legacy")
public class LegacyController implements Controller {
    public ModelAndView handleRequest(HttpServletRequest request, 
                                    HttpServletResponse response) { }
}

  • SimpleUrlHandlerMapping：显式配置的路径到处理器的映射。通过明确的配置将URL模式映射到具体的处理器bean，提供更直观的配置方式。

    <bean class="org.springframework.web.servlet.handler.SimpleUrlHandlerMapping">
    <property name="mappings">
        <props>
            <prop key="/admin/*">adminController</prop>
            <prop key="/static/**">resourceController</prop>
            <prop key="/api/v1/**">apiV1Handler</prop>
        </props>
    </property>
</bean>

  • RouterFunctionMapping：函数式断点的路由函数，这是Spring WebFlux引入的函数式变成，但在Spring MVC中也支持。使用RouterFunctionAPI定义路由：

    @Configuration
public class FunctionalRoutes {
    
    @Bean
    public RouterFunction<ServerResponse> route() {
        return RouterFunctions.route()
            .GET("/func/users/{id}", request -> 
                ServerResponse.ok().body(userService.findById(...)))
            .POST("/func/users", request -> 
                ServerResponse.ok().body(userService.create(...)))
            .build();
    }
}

  • PathPatternMatchableHandlerMapping：这不是一个独立的HandlerMapping实现，而是一个标记接口，表示支持Servlet 4.0+的PathPattern的映射器。

然后根据debug的方式来看，这里从IOC容器中获取的HandlerMapping有三个：RequestMappingHandlerMapping、SimpleUrlHandlerMapping、BeanNameUrlHandlerMapping。

2️⃣现在就是搞清楚不同的HandlerMapping有什么作用，以及它们的工作流程。

首先要来看下这些HandlerMapping在初始化的时候都做了哪些工作，我们才能知道它们getHandler()方法的具体逻辑。

对于BeanNameUrlHandlerMapping和SimpleUrlHandlerMapping而言，它的初始化工作相对简单。对于RequestMappingHandlerMapping而言，它继承了InitializingBean接口，所以在初始化的时候会执行afterProperties()方法。

具体的实现在RequestMappingHandlerMapping的父类AbstractHandlerMapping中的afterProperties()方法中：

	public void afterPropertiesSet() {
		initHandlerMethods();
	}
	
    protected void initHandlerMethods() {
        // 获取IOC容器中所有的beanName
		for (String beanName : getCandidateBeanNames()) {
            // 如果beanName不是以 scopedTarget. 开头的就执行
			if (!beanName.startsWith(SCOPED_TARGET_NAME_PREFIX)) {
                // 这一步是关键，它是RequestMappingHandlerMapping工作的核心步骤
				processCandidateBean(beanName);
			}
		}
		handlerMethodsInitialized(getHandlerMethods());
	}

一般而言，我们自己开发些的Controller都不会以scopedTarget开头的，所以基本上都会去执行processCandidateBean()这个方法：

   // 这个方法在AbstractHandlerMapping中
   protected void processCandidateBean(String beanName) {
		Class<?> beanType = null;
		try {
            // 获取当前Bean的类型
			beanType = obtainApplicationContext().getType(beanName);
		}
		catch (Throwable ex) {
			if (logger.isTraceEnabled()) {
				logger.trace("Could not resolve type for bean '" + beanName + "'", ex);
			}
		}
        // 如果能获取到当前Bean的类型并且当前的Bean是一个Handler
		if (beanType != null && isHandler(beanType)) {
			detectHandlerMethods(beanName);
		}
	}
	
	// 这个方法在RequestMappingHandlerMapping类中
	protected boolean isHandler(Class<?> beanType) {
        // 如果类上有@Controller或@RequestMapping注解标注
		return (AnnotatedElementUtils.hasAnnotation(beanType, Controller.class) ||
				AnnotatedElementUtils.hasAnnotation(beanType, RequestMapping.class));
	}

从IOC中获取到容器中所有的Bean的信息后，判断当前Bean所在的类上是否有@Controller标注或@RequestMapping标注，如果有的话就认为它是一个Hanlder，就需要调用detectHanlderMethods()方法来收集记录。

	// 这个方法的作用就是将Handler的一些信息都要记录到对应的Map中，这样在处理用户请求的时候就可以根据Map中的内容快速找到对应的Handler
	protected void detectHandlerMethods(Object handler) {
        // 如果handler是String类型的说明这个Hanlder对应的Bean还没有被初始化，所以根据不同的方法来获取到Handler的类型
		Class<?> handlerType = (handler instanceof String ?
				obtainApplicationContext().getType((String) handler) : handler.getClass());

		if (handlerType != null) {
            // 获取这个Handler的原始类（Handler有可能是被代理类，这里是找到它的原始类型）
			Class<?> userType = ClassUtils.getUserClass(handlerType);
            /**
             * 这一步是遍历Handler的原始类中所有的方法
             * 这里得到打methods的：
             * key - public java.lang.String com.example.controller.TestController.hello()
             * value - { [/test/hello]}
             * 实际上整理得到的Map它的Key是Handler的方法，而value是Handler的Path属性
             */
			Map<Method, T> methods = MethodIntrospector.selectMethods(userType,
					(MethodIntrospector.MetadataLookup<T>) method -> {
						try {
                            // 根据方法上的@RequestMapping注解的信息构建Handler的基本信息
							return getMappingForMethod(method, userType);
						}
						catch (Throwable ex) {
							throw new IllegalStateException("Invalid mapping on handler class [" +
									userType.getName() + "]: " + method, ex);
						}
					});
			// 这一步是将上面收集到的Handler的信息都进行注册（注册的时候会将key与value进行翻转）
			methods.forEach((method, mapping) -> {
				Method invocableMethod = AopUtils.selectInvocableMethod(method, userType);
				registerHandlerMethod(handler, invocableMethod, mapping);
			});
		}
	}

首先找到Handler对应的原始类，然后遍历原始类的中的每个方法找到标注了@RequestMapping的方法，将收集到的方法保存到一个Map中，这个Map的Key是Handler对应的Method本身，而Value是Handler对应的Path属性。此时就找到了所有的Handler以及它的Path之间的对应关系。为了方便根据Path来查找Handler，所有后面在注册的时候进行包装后Key与Value发生了翻转，进一步处理后的信息被存储在了AbstractHandlerMethodMapping的registry属性。

所以经过上面的总结与发现，可以看到HandlerMapping的作用就是根据一些特定的规则，将用户的所有的Handler都找到，并建立Handler的Method与Path之间的关联关系。这样，在处理用户的请求的时候，就可以根据用户的请求的Path属性找到对应的Handler来执行。

总得来说，初始化HandlerMapping的逻辑并不复杂，它借助的是InitializingBean接口的afterProperties()完成对所有Handler信息的收集。

简单说一下Bean初始化的过程：

执行Aware接口方法 ==> 执行BeanPostProcessor的postProcessBeforeInitialization()方法 ==> 执行InitializingBean的afterProperties()方法 ==> 执行 init-method 配置的方法 ==> 执行BeanPostProcessAfterInitialization()方法

所以之类的RequestMappingHandlerMapping是利用的InitializingBean接口的afterProperties()方法实现了

初始化HandlerAdapter

	private void initHandlerAdapters(ApplicationContext context) {
		this.handlerAdapters = null;

		if (this.detectAllHandlerAdapters) {
			// Find all HandlerAdapters in the ApplicationContext, including ancestor contexts.
			Map<String, HandlerAdapter> matchingBeans =
					BeanFactoryUtils.beansOfTypeIncludingAncestors(context, HandlerAdapter.class, true, false);
			if (!matchingBeans.isEmpty()) {
				this.handlerAdapters = new ArrayList<>(matchingBeans.values());
				// We keep HandlerAdapters in sorted order.
				AnnotationAwareOrderComparator.sort(this.handlerAdapters);
			}
		}
		else {
			try {
				HandlerAdapter ha = context.getBean(HANDLER_ADAPTER_BEAN_NAME, HandlerAdapter.class);
				this.handlerAdapters = Collections.singletonList(ha);
			}
			catch (NoSuchBeanDefinitionException ex) {
				// Ignore, we'll add a default HandlerAdapter later.
			}
		}

		// Ensure we have at least some HandlerAdapters, by registering
		// default HandlerAdapters if no other adapters are found.
		if (this.handlerAdapters == null) {
			this.handlerAdapters = getDefaultStrategies(context, HandlerAdapter.class);
			if (logger.isTraceEnabled()) {
				logger.trace("No HandlerAdapters declared for servlet '" + getServletName() +
						"': using default strategies from DispatcherServlet.properties");
			}
		}
	}

这里可以看到它跟initHandlerMappings()方法没有什么区别，它的逻辑就是从IOC容器中获取到所有类型为HandlerAdapter属性的Bean，然后将他们放入DispatcherSerlvet中的handlerAdapters属性中。

Spring MVC处理请求的逻辑

在Spring MVC启动的过程中，它会将Handler的Method与Path的对应关系建立完成。在最开始我们注入了一个DispatcherServlet属性，它本质上还是一个Servlet，所以它必须实现Servlet接口规定的一些方法，例如处理请求的service()方法。

我们顺着HttpServlet的service()方法往下找的话，最终会找到接口的处理起点是DispatcherService的doService()方法：

	protected void doService(HttpServletRequest request, HttpServletResponse response) throws Exception {
        // 记录传入请求的基本信息（如URL、方法等）主要用于调试和监控
		logRequest(request);

		// 处理include请求（不过多展开，感兴趣可以自行搜索）
		Map<String, Object> attributesSnapshot = null;
		if (WebUtils.isIncludeRequest(request)) {
			attributesSnapshot = new HashMap<>();
			Enumeration<?> attrNames = request.getAttributeNames();
			while (attrNames.hasMoreElements()) {
				String attrName = (String) attrNames.nextElement();
				if (this.cleanupAfterInclude || attrName.startsWith(DEFAULT_STRATEGIES_PREFIX)) {
					attributesSnapshot.put(attrName, request.getAttribute(attrName));
				}
			}
		}

		// 将Spring MVC的核心组件都放到请求的上下文中
		request.setAttribute(WEB_APPLICATION_CONTEXT_ATTRIBUTE, getWebApplicationContext());
		request.setAttribute(LOCALE_RESOLVER_ATTRIBUTE, this.localeResolver);
		request.setAttribute(THEME_RESOLVER_ATTRIBUTE, this.themeResolver);
		request.setAttribute(THEME_SOURCE_ATTRIBUTE, getThemeSource());

		if (this.flashMapManager != null) {
			FlashMap inputFlashMap = this.flashMapManager.retrieveAndUpdate(request, response);
			if (inputFlashMap != null) {
				request.setAttribute(INPUT_FLASH_MAP_ATTRIBUTE, Collections.unmodifiableMap(inputFlashMap));
			}
			request.setAttribute(OUTPUT_FLASH_MAP_ATTRIBUTE, new FlashMap());
			request.setAttribute(FLASH_MAP_MANAGER_ATTRIBUTE, this.flashMapManager);
		}

		RequestPath previousRequestPath = null;
		if (this.parseRequestPath) {
			previousRequestPath = (RequestPath) request.getAttribute(ServletRequestPathUtils.PATH_ATTRIBUTE);
			ServletRequestPathUtils.parseAndCache(request);
		}

		try {
            // 核心方法，用于分发请求到具体的Handler上
			doDispatch(request, response);
		}
		finally {
			if (!WebAsyncUtils.getAsyncManager(request).isConcurrentHandlingStarted()) {
				// Restore the original attribute snapshot, in case of an include.
				if (attributesSnapshot != null) {
					restoreAttributesAfterInclude(request, attributesSnapshot);
				}
			}
			if (this.parseRequestPath) {
				ServletRequestPathUtils.setParsedRequestPath(previousRequestPath, request);
			}
		}
	}

对于doService()方法而言，它主要负责的任务是：

  1. 记录请求的日志
  2. 为请求准备必要的上下文环境
  3. 调用核心的请求分发方法doDispatch()来处理请求
  4. 在请求处理完成后，进行资源清理和环境恢复

主要关注的是doDispatch()方法，它是用于请求分发的核心方法：

	protected void doDispatch(HttpServletRequest request, HttpServletResponse response) throws Exception {
		HttpServletRequest processedRequest = request;
		HandlerExecutionChain mappedHandler = null;
		boolean multipartRequestParsed = false;

		WebAsyncManager asyncManager = WebAsyncUtils.getAsyncManager(request);

		try {
			ModelAndView mv = null;
			Exception dispatchException = null;

			try {
                // 检查是否是文件上传类型的请求
				processedRequest = checkMultipart(request);
				multipartRequestParsed = (processedRequest != request);

				// 从加载中准备的映射信息中获取一个Handler
				mappedHandler = getHandler(processedRequest);
				if (mappedHandler == null) {
                    // 如果获取不到对应的Handler信息就直接返回404
					noHandlerFound(processedRequest, response);
					return;
				}

				// 如果获取到的Handler，就需要根据这个Handler得到一个HandlerAdapter
				HandlerAdapter ha = getHandlerAdapter(mappedHandler.getHandler());

				// 获取到方法的名称
				String method = request.getMethod();
                // 判断请求的方法
				boolean isGet = HttpMethod.GET.matches(method);
				if (isGet || HttpMethod.HEAD.matches(method)) {
					long lastModified = ha.getLastModified(request, mappedHandler.getHandler());
					if (new ServletWebRequest(request, response).checkNotModified(lastModified) && isGet) {
						return;
					}
				}

				if (!mappedHandler.applyPreHandle(processedRequest, response)) {
					return;
				}

				// Actually invoke the handler.
				mv = ha.handle(processedRequest, response, mappedHandler.getHandler());

				if (asyncManager.isConcurrentHandlingStarted()) {
					return;
				}

				applyDefaultViewName(processedRequest, mv);
				mappedHandler.applyPostHandle(processedRequest, response, mv);
			}
			catch (Exception ex) {
				dispatchException = ex;
			}
			catch (Throwable err) {
				// As of 4.3, we're processing Errors thrown from handler methods as well,
				// making them available for @ExceptionHandler methods and other scenarios.
				dispatchException = new NestedServletException("Handler dispatch failed", err);
			}
			processDispatchResult(processedRequest, response, mappedHandler, mv, dispatchException);
		}
		catch (Exception ex) {
			triggerAfterCompletion(processedRequest, response, mappedHandler, ex);
		}
		catch (Throwable err) {
			triggerAfterCompletion(processedRequest, response, mappedHandler,
					new NestedServletException("Handler processing failed", err));
		}
		finally {
			if (asyncManager.isConcurrentHandlingStarted()) {
				// Instead of postHandle and afterCompletion
				if (mappedHandler != null) {
					mappedHandler.applyAfterConcurrentHandlingStarted(processedRequest, response);
				}
			}
			else {
				// Clean up any resources used by a multipart request.
				if (multipartRequestParsed) {
					cleanupMultipart(processedRequest);
				}
			}
		}
	}

这里需要知道的是为什么从映射中拿到的不是Hander，而是HandlerAdapter。因为在Spring MVC中创建Handler的方式有很多种，每个Handler对用于请求响应也是不同的。所以这里，我们会根据映射关系得到Handler的一些信息后，可以根据Handler的类型找到一个HandlerAdapter，然后只需要执行HandlerAdapter的handler()方法就可以了。
